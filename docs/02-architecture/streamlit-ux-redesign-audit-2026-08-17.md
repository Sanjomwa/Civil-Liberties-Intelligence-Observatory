# Streamlit UX/IA Audit — 2026-08-17

Status: Complete — analysis only, no application code changed (see "What was built this pass")
Author: Claude Code (Sonnet 5), advisory judgment from Fable 5 per `CLAUDE.md`'s model-routing policy
Scope: all 9 Streamlit pages, `streamlit/core/`, `streamlit/components/`, `streamlit/services/marts.py`, `streamlit/app.py`

## Why this document exists

Requested directly by the project owner, in his own words: *"I am not seeing anything on anomaly and blocked graph against the regime classification from ACLED. I think we might need a redesign of the streamlit pages but we need it from a fable advisory straight from the codebase... I am not doubting the observations just the way our streamlit layer is I think we can do better."*

This is a whole-layer audit, not a single-bug patch. It follows immediately after TD-96 (color/contrast fixes) and a first TD-95 Phase 0 pass (attribution-language copy fixes), both shipped 2026-08-17 — this document is the "next tier" question those two passes didn't ask: does the layer, as a whole, actually serve CLIO's real intended users.

Every claim below was checked directly against the live repository and the live BigQuery warehouse (`encoded-joy-485413-k5`) during this session — not inferred from the 2026-08-15 Opus design pass (which reviewed this code secondhand) or from this prompt's own assertions. Where I found this prompt's own hypothesis to be imprecise, I say so rather than silently working around it.

## Step 0 — the specific complaint, investigated and confirmed (precisely bounded)

**Confirmed, exactly as hypothesized, for two tables — and explicitly *not* true for a third table that looked like it might be a second instance of the same gap.**

Directly verified:

- `grep -rn "ooni_acled_lag_correlation\|ooni_weekly_signals" streamlit/` → **zero matches**, live repo, not a snapshot.
- Both tables are real, current, and non-trivial:
  - `intelligence.ooni_acled_lag_correlation`: 5,500 rows, data through `2025-06-28`.
  - `features.ooni_weekly_signals`: 550 rows, data through `2025-06-28`.
- Neither table has *any* downstream consumer, anywhere — not Streamlit, and not another Bruin asset (`grep -rl` across `Bruin/assets/reporting/` and `Bruin/assets/marts/` returns nothing for either name). They are genuine dead ends in the DAG: built, validated, real findings logged in ADR-0011's own "Consequences" section, and then never connected to anything downstream.
- ADR-0011 itself states this was deliberate, not an oversight: *"No Streamlit rendering was built in this session, by explicit scope — a future session wires either series into the dashboard once the project owner has reviewed what the correlation numbers actually look like."* Sam's complaint **is that review arriving**. The right framing for the recommendation below is not "an oversight was found," it's "the stated precondition for wiring this in has now been met."

**What I checked and ruled out as a false positive:** `intelligence.protocol_lag_relationships` looked, on table name alone, like it might be a second orphaned analytical product. It is not. It's an upstream intermediate table in the *consumed* OONI path: `features.protocol_daily_signals` → `intelligence.protocol_signal_regimes` + `intelligence.protocol_lag_relationships` → `intelligence.protocol_relationships` → the reporting marts that Protocol Intelligence, the Correlation Engine, ASN Behavioral Intelligence, and the Methodology page all already read from. Its content does reach the dashboard, indirectly, through that downstream aggregation — it's simply not meant to be queried directly by Streamlit, the same as no page queries `stg.ooni_measurements` directly either. I'm flagging this explicitly because the natural instinct on seeing an unfamiliar `intelligence.*` table name is to assume it's another gap; checking the actual dependency graph (`architecture-assessment.md`'s declared lineage, cross-checked against `Bruin/assets/*/*.sql`'s `depends:` headers) is what avoids a false "second gap" finding.

### What Sam's complaint actually decomposes into (two different design problems)

His literal ask — "anomaly and blocked graph against the regime classification" — is **two series with real variation**, not a null result to design around:

- `features.ooni_weekly_signals` carries two independently-tracked series per `(week_start_date, test_name)`: `anomalous_*` (from `int.ooni_measurement_verdicts`) and `blocked_*` (from `int.ooni_experiment_results`), deliberately never merged (ADR-0011's whole point — echoing the same "disclose disagreeing layers side by side" principle already established for the LLM extraction layer per ADR-0009). Both are Saturday-anchored, matching `intelligence.acled_pressure_regimes`' own anchor — the join Sam is asking for already lines up cleanly on `week_start_date` with no date-math needed.
- Real variation exists to show: Signal's ANOMALOUS rate moves, and `psiphon`'s flat zero-variance line (never anomalous, never blocked, across the entire window) is itself a legitimate, interesting finding — a visual contrast between an active protocol and a quiet one, not two flat lines.

This half is **small, safe, and worth building now** — see "What was built this pass" below.

The second, harder half is `intelligence.ooni_acled_lag_correlation` — the lag-tested *correlation strength* between those series and ACLED's regime severity. Its own ADR is blunt about the honest result: *"computable correlations are weak (mean `|corr|` mostly 0.10–0.31)... no `STRONG_RELATIONSHIP` state observed anywhere, `MODERATE_RELATIONSHIP` only a handful of individual weeks"* — and the one `MODERATE_RELATIONSHIP` row that did briefly exist was later found to be a misclassification artifact and disappeared entirely (TD-93). Displaying this data naively — a grid of −2..+2 lag columns mostly reading `WEAK_OR_NO_RELATIONSHIP`/`ZERO_VARIANCE_WINDOW` — would look like a broken or empty chart to a first-time visitor, exactly the failure mode this project's own methodology page already knows how to avoid (see the "Correlation Strength: Historical Track Record" section, which reports "N of M rows ever qualified" as a plain count rather than trying to visualize a mostly-null field). I'm **not** recommending a naive chart here; see Recommendation R1 below for the specific design.

## Step 1 — who this actually needs to serve, and whether it does

`README.md` (line 119) states: *"A dedicated Welcome page orients first-time visitors... a suggested reading order by role (journalist/NGO/legal reader vs. methodology reviewer)."* I checked this against the live `welcome.py`, not just taking the README's word for it: **it's accurate.** The "Suggested reading order" section exists, in a real usable form, with exactly those two named paths (lines 145–167 of `welcome.py`) — each a numbered 3-step sequence through specific pages, plus a one-line rationale under the journalist/NGO path ("These are CLIO's two identified primary users — both need a citable, attributed finding, not a raw score"). This is a genuine strength, not aspirational documentation ahead of the build. Say so plainly: the Welcome page is well-built for its stated job.

`docs/01-product/product-assessment.md` gives the fuller buyer table behind that two-persona simplification: investigative journalists, digital-rights NGOs, academic researchers, election observer missions, human rights commissions/legal teams, eventually corporate risk/compliance — with journalists and small-NGO researchers named explicitly as the fastest-closing, most price-sensitive segment, and the *pressure-attribution decomposition* (splitting one composite score into named, sourced drivers) named as "the sharpest available expression" of CLIO's differentiated value. That document's own words, not mine — and it matches what I found reading the code: `pressure_attribution.py` is, on direct read, the most disciplined page in the layer (see Step 2).

### Walking the two stated reading paths

**Journalist/NGO/legal reader** (Pressure Attribution → Finance Bill 2024 → Methodology): this path works. Pressure Attribution answers "why is pressure elevated, specifically" with named, weighted, sourced terms and grain-honesty callouts throughout. Finance Bill delivers the flagship case study with its own honest headline ("a conflict-confirmed window with weak-to-absent protocol-layer statistical correlation, not a synchronized-escalation finding"). Methodology closes the loop on how to cite responsibly. No breakdown found in this path.

**Methodology reviewer** (Methodology → Protocol Intelligence → Pressure Attribution): mostly works, with one real gap. The Methodology page's own "System Architecture" section (lines 49–86) describes a **four-layer, OONI-only stack** — "Raw Measurement Ingestion: OONI network measurements, protocol observations, platform accessibility signals" — and never names ACLED as an ingestion source anywhere in that section, despite ACLED conflict-event data driving 75% of the composite pressure score (ADR-0004) and the ACLED path A regime taxonomy (STABLE→CRISIS) now rendering on two live pages (National Stress Observatory, Pressure Attribution). A methodology reviewer reading this page top-to-bottom to evaluate CLIO's rigor would come away not knowing the majority-weight input to the headline score exists, let alone how it's classified. This is a real documentation gap on the exact page whose job is to prevent exactly that outcome — see Finding F1 below.

## Step 2 — findings across the whole layer

### Information architecture

The current 9-page structure (Welcome + 8 content pages) is not, on the whole, organized around pipeline internals dressed up as pages — most pages map to a real question ("why is pressure elevated right now," "what happened during the Finance Bill protests," "which networks show the strongest evidence"). One clear exception:

**F0 (High): three pages are the same underlying analysis at three different slices, not three different questions.** Directly confirmed in `services/marts.py`: `get_protocol_correlation()` (Correlation Engine, line 264), `get_event_explorer()` (Suppression Event Explorer, lines 428–429, same mart plus a join for extra columns), and the first half of `get_finance_bill_incident()` (Finance Bill report, line 514) **all three select from `reporting.protocol_repression_correlation_mart`**, with near-identical column sets (`rolling_pressure_corr`, `correlation_state`, `alignment_state`, `divergence_state`, `protocol_stress_score`). The Correlation Engine and Suppression Event Explorer in particular are close to the same page with different date-filtering defaults and a different chart layout — a visitor exploring "what happened around date X" has to know in advance which of two nearly-identical pages has the view they want. Compounding this: "Suppression Event Explorer" is the page whose title most overclaims a settled finding (flagged separately under TD-95, copy-fixed but not renamed this pass, deliberately deferred — see below) — and its honest content is, like the Correlation Engine's, weak-to-null correlation almost everywhere in the historical record (per the Methodology page's own track record: 0 rows have ever reached STRONG, and MODERATE is a handful of rows total, system-wide, across all history). Two pages both built around a field whose true story is "we checked, it's weak" is a case where consolidation would also make the honest-null story easier to tell once, well, instead of twice, thinly.

**Recommendation R2 (High, IA): merge Suppression Event Explorer into Protocol ↔ Repression Correlation Engine.** Concretely: fold the Event Explorer's per-date-selection heatmap and divergence scatter into the Correlation Engine as a second tab, keeping the Correlation Engine's per-protocol drill-down as the first tab — the `st.tabs()` pattern is already proven in this codebase (`protocol_intelligence.py`, lines 149–152), so this isn't introducing a new UI pattern. This removes one page from the nav (9 → 8), removes the near-duplicate query path, and lets the "no glazing" honest-null disclosure live in one place instead of two. This also removes the need to separately resolve the "Suppression Event Explorer" title-overclaim question raised (and deliberately deferred) under TD-95 Phase 0 — a merged page can be titled around what it actually shows.

**F1 (Medium): the Methodology page under-documents the ACLED path.** See Step 1 above. `st.subheader("System Architecture")`'s four-layer description names only OONI as raw input. **Recommendation R1b: add ACLED conflict-event ingestion as a named input in that section**, and add the regime taxonomy table (STABLE/MOBILISATION/CONFLICT/REPRESSION/CONTESTATION/ESCALATION/CRISIS — currently explained only inline, informally, on Pressure Attribution at line 134–146) to the Methodology page alongside the existing "Protocol Regime Classification" and "Correlation Alignment States" tables (lines 189–244), which already establish the right pattern (regime name → plain-English meaning, in a `st.dataframe`) — this is copying an existing good pattern to a gap, not inventing a new one.

### Completeness

**F2 (High): confirmed exactly two terminal orphan tables** — `intelligence.ooni_acled_lag_correlation` and `features.ooni_weekly_signals` (Step 0, above). I checked every table in `intelligence.*` and `features.*` against `services/marts.py`'s actual `FROM`/`JOIN` clauses (not declared headers) to look for a third instance of this pattern; found none. `intelligence.country_initialization_status` and `intelligence.country_readiness` are correctly unconsumed by Streamlit — they're pipeline-internal state for the multi-country scaffolding, not analytical products meant for an end user, and don't belong in this audit's scope.

**Recommendation R1 (High): wire `ooni_weekly_signals` in now (see "What was built" below); design, but do not yet build, a display for `ooni_acled_lag_correlation`.** For the lag-correlation table specifically: follow the Methodology page's own established pattern for a mostly-null field — a plain count disclosure ("X of Y (test_name, lag) combinations have ever reached MODERATE or STRONG, across all lags and weeks; the largest magnitude observed is Z"), not a heatmap grid that would visually read as broken. If a specific week/lag combination ever does cross the threshold in future data, surface that instance by exception (a callout, the way Pressure Attribution already surfaces exceptional weeks), not as the default view. This is the same shape of design problem the Correlation Engine and old Event Explorer already have today (see F0/R2) — solve it once, in the merged page from R2, rather than building a fourth place with the same null-result-design problem.

### Redundancy / dead scaffolding

**F3 (Low): three purpose-built shared helpers have zero adopters.** `components/charts.py`'s `empty_figure()` and `add_threshold_lines()`, and `components/tables.py`'s `render_table()` and `latest_by_group()`, are referenced by **zero** pages (`grep -rln` across `streamlit/pages/` returns nothing for any of the four names). Every page hand-rolls its own `st.warning("No ... available"); st.stop()` pattern instead (functionally fine, and consistent enough on its own — this is not a correctness bug) and hand-rolls repeated `fig.add_hline(...)` calls for threshold lines (I directly confirmed 3 separate `add_hline` calls in `national_stress_observatory.py` alone, and 4 more in `protocol_repression_correlation_engine.py`, each of which is exactly what `add_threshold_lines()` was built to replace). **Recommendation: either adopt these three helpers where the matching pattern already exists (the threshold-line and empty-state call sites are trivial swaps, low risk), or delete them** — right now they're maintained code with no effect on the live app, which is its own small tax.

**F4 (Low): `core/layout.py` is an empty stub**, four lines of docstring, no code, never imported anywhere. Low severity, no user-facing effect — noted for the same reason as F3: it's upkeep with no payoff either way. Delete or fill; either is fine, leaving it as a stub indefinitely is the only bad option.

**F5 (Low): `core/constants.py`'s `PAGES` list is dead and stale.** `grep -rn "\bPAGES\b" streamlit/` finds the definition and nothing else — zero consumers. The real navigation is defined independently in `app.py`'s `st.navigation([...])` call (confirmed by direct read), which is itself correct and current. But `PAGES` still lists **"Protocol Regime Monitor"** — a page name `protocol_intelligence.py`'s own caption (line 87) says was retired and consolidated under TD-16. This isn't a live bug (nothing reads this list), but it's exactly the kind of stale-but-silent constant that becomes a real bug the day someone adds a page and updates `PAGES` by copy-paste instead of checking whether anything still consumes it. **Recommendation: delete `PAGES` entirely** — `app.py`'s `st.navigation()` call is already the single source of truth and doesn't need a shadow copy.

### Weak/null-result handling

This is a genuine strength almost everywhere I checked, worth stating plainly rather than manufacturing a complaint to fill out this section. Direct examples: Finance Bill's executive summary explicitly states "this is a conflict-confirmed window with weak-to-absent protocol-layer statistical correlation, not a synchronized-escalation finding... that disagreement is the honest result, not something to resolve toward the stronger-sounding claim" (lines 101–104). Both the Correlation Engine and (soon-to-be-merged, per R2) Suppression Event Explorer already conditionally render different copy depending on whether any row in the selected window actually qualifies as MODERATE/STRONG, rather than showing a number with no context. The Methodology page's "Correlation Strength: Historical Track Record" section is the strongest instance in the whole layer — a live-queried, honestly-reported count of how often thresholds have *ever* been crossed, with an explicit statement that the thresholds are inherited defaults, not recalibrated to manufacture more findings.

The one place this discipline is *not* yet applied is the gap identified in F2/R1 above — because that data was never wired in at all, there was no chance to apply it. Once R1 is built, it should follow this same house pattern, not invent a new one.

### Visual / interaction, next tier after TD-96

**F6 (Medium): the global date-filter sidebar renders identically on every page, including two pages that ignore it entirely.** `core/filters.py`'s `render_sidebar()` is called by every page via each page's own `init_state()`/`render_sidebar()` boilerplate, and always shows "Start date" / "End date" controls with the caption "Global filters persist across pages." But `asn_behavioral_intelligence.py`'s `get_asn_behavior()` takes no date arguments at all (confirmed: the function signature has zero parameters, and the page's own trust strip hardcodes `max_date="Latest Profile Snapshot"` rather than using the filtered range) — it's a full-history snapshot mart with no date dimension, by design (the page's own data source, `asn_behavior_profile_mart`, is explicitly a lifetime summary per the TD-02 fix already on record). The Methodology page similarly never uses the date filter. A visitor changing the date range on either page gets no feedback that the control did nothing. **Recommendation: either scope the sidebar to only render the date filter on pages that consume it (Streamlit's per-page config supports this cleanly), or add a one-line caption on the two exempted pages noting the date filter doesn't apply here** (matching the "grain honesty" pattern this project already uses everywhere else, e.g. `pressure_attribution.py`'s explicit weekly/semiannual grain callouts).

**F7 (Low): ASN Behavioral Intelligence's chart labels are dense jargon for its stated audience.** "Maturity Signal," "Behavior Priority," "behavioral_class" as a raw KPI label — this page is aimed at the same journalist/NGO audience as the rest of the layer (per the Welcome page's page guide), but its labels read like they were copy-pasted from column names rather than translated the way Pressure Attribution's are (e.g. "Conflict Share," not `conflict_share_pct`). Low severity because the page does have one plain-English `st.markdown("**Plain English** ...")` block already (proving the intent exists) — just inconsistently applied to the KPI row and chart above it.

**F8 (Low): title/icon inconsistency between `welcome.py`'s page guide and `app.py`'s live navigation.** Checked directly: these currently match exactly (both list the same 8 pages, same emoji, same order) — flagging this as a **non-finding**, explicitly, so a future session doesn't have to re-check it. The one place a mismatch *does* exist is the dead `PAGES` constant (F5), not the guide itself.

**F9 (Low, unverified): journalist-article screenshot fitness was not directly tested.** The prompt asked specifically whether pages "would screenshot well for a journalist's article." I did not test this against a real embed (no way to render the app visually in this environment — see the same limitation noted in this session's earlier TD-96 report). One honest observation from reading the CSS and chart code directly: every chart uses `core/theme.py`'s dark `PALETTE["bg"]` (`#0D0D0F`) via `apply_layout()`, with no light-theme variant anywhere in the codebase. A journalist embedding a chart into a light-background article would either need to keep the dark panel as an image (common enough practice, not necessarily a problem) or manually strip the background — this hasn't been designed for either way, and I'm not confident enough in an untested guess to recommend a specific fix. Flagging as open, not resolved.

## What's already good — said plainly, not manufactured to balance the report

- The Welcome page's role-based reading order is real, accurate to its own README claim, and well-targeted at CLIO's actual documented buyer table.
- Pressure Attribution is the strongest page in the layer: named/sourced/weighted decomposition, grain-honesty callouts at every join, and it matches `product-assessment.md`'s own independent claim that this decomposition is CLIO's sharpest differentiator.
- The "no glazing" discipline (state weak/null results plainly rather than manufacturing false precision) is applied consistently almost everywhere it matters — Finance Bill's executive summary and the Methodology page's historical track-record section are the clearest examples, and this is a genuinely disciplined pattern this project should keep leaning on as it wires in the new R1/R3 content, not something this audit needed to invent.
- Source attribution and license compliance (`components/trust.py`'s `attribution_footer`) is handled once, correctly, in a shared component every page calls — exactly the kind of shared infrastructure this audit's "redundancy" section wishes existed more of elsewhere (F3).
- TD-96's color/contrast fixes and this session's own TD-95 Phase 0 copy fixes are both real, live-verified (via `AppTest` against real BigQuery data, not just a syntax check) — noted here because they're the direct predecessor to this document, and nothing in this audit found either to be inadequate at the layer they addressed.
